April 10, 2025 – CSS-BADE Bi-Weekly Knowledge Sharing (Cascade Architecture Evolution): Internal knowledge-transfer session led by Benjamin for the Customer Services & Solutions – Business Analytics Data Eng. (CSS-BADE) team. Here Benjamin delivered a comprehensive history and architecture review of "Cascade" (the data-driven communications platform). He started from Cascade's inception (a P2 retargeting POC that used Hadoop/Alpaca to filter consent-compliant segments), then traced its evolution: building the EOS API and Engagement Studio UI in early 2021, implementing "clean rooms" (separate data silos for each marketing consent purpose) in lieu of a not-yet-ready Immuta tool, and eventually migrating all data to Unity Catalog Delta Lake for better governance. During the talk, he shared a Visio architecture diagram outlining the complex consent bifurcations across legacy apps, new apps, and printers – and how Cascade's Consent State Table was built to simplify using the correct consent flag for each scenario. He also discussed challenges like orphaned email consent records (due to users updating emails in HPID) and described a custom solution he implemented to reconcile those, underlining his role in closing architecture gaps to ensure compliance. Recording: Accessible on HP SharePoint (OneDrive) as "CSS BADE Developers Knowledge Sharing Session – 2025-04-10". Associated Files: A PDF transcript of the session is available, and Benjamin's Visio diagrams (e.g. "Consent Current State Architecture") were shared during the call.

May 28, 2025 – Phani–Ben 1:1 Sync (Real-Time Telemetry Pipeline Design): Private knowledge transfer meeting between Benjamin and Phani Kiran (his successor). In this recorded 1:1, Benjamin outlined a new streaming data pipeline to handle Instant Ink printer telemetry (events like cartridge insertions and ink levels) in near-real-time. He suggested using an AWS event queue (Amazon Kinesis) feeding Databricks to process 50 million daily events into Unity Catalog Delta tables. Benjamin had calculated costs – about $50/day for 50M events ($1.5K/month), plus ~$1.2K for AWS Lambda and ~$100 for Databricks – and compared this ~$2.7K/month solution to an alternative that would cost "$1000 a day" using legacy methods. He and Phani discussed the pros/cons of building a fresh pipeline vs. relying on existing daily batch data: Benjamin noted the existing pipeline only provided weekly snapshots, missing real-time needs. This session captured Benjamin's strategic thinking on balancing data latency vs. cost, and showcased him mentoring Phani on the design decisions. When Phani raised the possibility that such IoT data might already be captured by another team ("Pepto" telemetry pipeline), Benjamin acknowledged that if so, duplicating it would be unnecessary – demonstrating his pragmatic approach. They actually pulled in a data architect (Meena Elango) mid-call to confirm where "low ink" events land, turning it into a group solution-finding effort. In summary, Benjamin provided architectural guidance on streaming data ingestion, cost optimization, and cross-team data sources, directly preparing Phani to manage those systems. Recording: Available internally as "Connect Phani_Ben – 20250528 Meeting Recording (MP4)" (OneDrive link shared with Phani).

Here, Benjamin went into whiteboard mode to review Cascade's end-to-end design for Phani. He reiterated how privacy "clean rooms" are used: e.g. one clean room for analytics and separate ones for each marketing channel. He explained that the EOS API and Engagement Studio work in tandem – Engagement Studio is the marketer-facing UI where campaign rules are defined, and it pulls its dropdown options (fields, tables) from the EOS API, which in turn reads from Cascade's Unity Catalog tables. In the session, Benjamin likely shared visuals (he mentions "let's call this Engagement Studio…Sean's team built the interface and we built the API") to illustrate the integration. He clarified that publishing a campaign in Engagement Studio triggers a job via the EOS API, which then queries the appropriate Delta tables in the consent-specific clean room to generate the target segment. This conversation gave Phani a clear mental model of how Cascade's pieces fit together – from raw data in Unity Catalog, through consent filters ("clean rooms"), through the EOS service, to the front-end Studio used by CRM managers. Benjamin's detailed walk-through (including a real example of a campaign definition and how the system ensures only consent-approved data is used) was invaluable knowledge transfer. Jan 7, 2026 – Cascade Email-CRM Team Weekly Connect: Weekly technical sync between the Cascade platform team and CRM Data team. In this meeting (recorded as "Cascade-Email CRM Team Weekly Connect – 20260107"), Benjamin actively troubleshot campaign segmentation issues and shared improvements. For example, CRM engineer Sravan Yella raised limitations of Adobe Engagement Studio (lacking visibility into SQL or failure reasons). Benjamin responded enthusiastically with news that his team was building a portal to expose the underlying Databricks SQL queries and job status for each segment. "We're getting close to having a portal where you can log in and see all that information, including the SQL for each job," he noted, describing it as a custom solution to help both his engineers and partners like Sravan's team. He confirmed this portal would bypass the limited UI of Engagement Studio by hooking directly into the Databricks jobs (since "Engagement Studio is just a front end…our Databricks cluster is running those SQL queries"). Later, when discussing migrating segments from Engagement Studio to pure Databricks, Benjamin advised caution: Engagement Studio's API automatically enforces privacy filters that a custom Databricks job might miss. He emphasized that any custom pipeline must replicate those consent filters ("the additional privacy consent filtering logic that the API is handling") and pointed out that no current Cascade campaigns run outside the sanctioned API for that reason. Overall, in this call Benjamin served as architectural expert and advisor, sharing a forthcoming internal tool to improve transparency and ensuring the CRM team understood Cascade's guardrails (consent checks, data flows) before attempting any alternatives. His contributions improved the team's ability to troubleshoot and plan future enhancements. Recording: Available on SharePoint as "Cascade-Email CRM Team Weekly Connect-20260107 Meeting Recording".
